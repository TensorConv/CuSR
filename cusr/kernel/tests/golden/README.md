# Parity goldens — P1 in-process CO

Byte-for-byte parity reference for the in-process CO drop-in
(`docs/kernel/INPROCESS_CO_PLAN.md`). Every later step (single-call parity,
parity-under-reuse, status-branch span, end-to-end) compares the `.so` output
against these blobs.

## Layout
```
golden/<variant>/<pop>/<blob>
```
- `variant` ∈ {`fd`, `ad`} — pinned per MUST-FIX #1: AD `.so` vs AD golden,
  FD `.so` vs FD golden, never cross-variant.
- `pop`:
  - `pop1000`     = `data/fixtures/pop.bin` (real EvoGP dump, M=1000, K_max=8)
  - `operon4000_g100` = `data/workload/snapshots/operon_feynman_I.12.1_pop4000_noise0_len64_seed0/pop_gen0100.bin`
    (M=4000, K_max=28 — high-K, stresses Cholesky / fail paths)
- blobs: `c_final.bin` (f32, total_c), `status.bin` (i32, M_prob). AD additionally
  has `loss_init.bin` / `loss_final.bin` (f32, M_prob).

`manifest.json` records sha256 + the pop header stats + the exact `max_iter` and
NVCC flags used.

## Provenance / regeneration
Generated by running the standalone (`batch_lm` / `batch_lm_ad`) at
`--max-iter 50`, built with the repo's `NVCC_FLAGS`
(`-O2 -arch=sm_80 -std=c++17 -lineinfo --use_fast_math`) on A100 sm_80.
Byte-parity is FMA-contraction sensitive — a rebuild that changes codegen, or a
different `max_iter`, will legitimately change these blobs.

To regenerate (GPU pinned, device idle):
```
source scripts/env.sh
cd cusr/kernel && make batch_lm batch_lm_ad
export CUDA_VISIBLE_DEVICES=2
uv run python cusr/kernel/tests/gen_golden.py
```

`test_inproc_parity.py` asserts (1) the standalone is byte-deterministic
run-to-run and (2) a fresh standalone run still reproduces these goldens.
