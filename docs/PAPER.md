## 一、先把测试环境弄干净（跑任何正式实验前，做一次）

- [ ] **1. 锁住显卡频率。** 现在所有结果都标着"频率没锁、数据只算草稿"。用刚批下来的管理员权限，把一张卡的频率锁死、记下锁定的数值，跑完再解开。不锁，所有速度数字都不能写进论文。
- [ ] **2. 让扫描脚本用上新的求导方法。** 我们最近做好的"反向求导"（算梯度更快的那套）还没接进扫描脚本——脚本现在跑的还是旧的前向求导。这一步要改脚本，把新方法加进去。不改的话，重跑出来的还是旧方法的数，等于白跑。
- [ ] **3. 重新编译，先和 scipy 对一遍答案。** 确认新方法算出来的数值是对的（之前对过 68 道、全过），再去烧显卡时间。

## 二、核心算法的实验结果（论文的主角，我负责）

- [ ] **4. 跑一次硬件性能剖析。** 看核心计算到底卡在哪：算力不够、内存带宽不够、还是指令发不过来。（业内叫 roofline，就是"看瓶颈在哪条线上"。）这个结论直接决定后面还要不要做内存布局那类优化——卡在指令上，那类优化就不用做了。
- [ ] **5. 重跑规模扫描。** 把这几个轴各扫一遍——群体多大、每棵树多少数据点、树多复杂——新旧两种求导方法 + CPU 上的 Operon 都放进去比，每个点都过一遍双精度质量检查。这是论文里最主要的那张性能表/图。
- [ ] **6. 出一张"反向求导比前向求导快多少"的对比。** 顺手就有，用来证明换方法值得。

## 三、真接进去用得省（第三块贡献：跑出干净结果才写满，否则缩成一小节）

- [ ] **7. 热启动。** 让下一代从上一代已经拟合好的常数接着算，迭代次数从 50 次降到 5–10 次。跑出来干净 → 论文就有完整的三块贡献；跑不出来 → 这块缩成一小节。
- [ ] **8. 同样时间下对比。** 给一样的墙上时间，比三种做法：完全不拟合常数 / 每代从头拟合 / 热启动只拟合几步。
