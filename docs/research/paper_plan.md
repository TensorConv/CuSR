# CuSR HPEC 论文怎么拼(6 页)

更新 2026-06-23。这份文件说清楚三件事:三个贡献怎么分、6 页地方怎么分、C1 和 C3 各有哪些可选的材料。

这份是现在的准。`OUTLINE.md`、`contributions.md`、`experiment_plan.md` 已经按下面这两条改成一致了:

- **C3 改成"把 kernel 装进 EvoGP 里用"**,不再是旧的"实证刻画"。原来 C3 里"什么时候快、什么时候慢"那部分,挪到 C2 的评测里讲。
- **reverse-AD 放进 C2**,当 kernel 最核心的技术。旧文档里"现在别做 reverse-AD"那句作废——它已经做完也验证过了,而且实测算 Jacobian 占整个循环 60–66% 的时间,是最值得做的一块。
- 红线不变:**不能说"CO 有用"**(这是别人早证过的)。C3 只说"装进去用得起、用得省",不说"CO 让 SR 变好"。

## 三个贡献

| | 贡献 | 是什么 | 重点 |
|---|---|---|---|
| **C1** | workload 和 benchmark | 说清楚"哪种 SR 题真的需要在函数内部拟合常数",并证明现有题库里这种题很少 | 判据 + 自己构造的题集 + 题库审计 |
| **C2** | GPU kernel(主角) | 一个 CUDA kernel,一次给一大批结构不同的树做二阶 LM 常数拟合 | reverse-AD + fp64 兜底检查 + 性能剖析(ncu SOL+warp-stall 为主, instruction roofline 作图) + 同条件对比 |
| **C3** | 装进 EvoGP 里用 | 把 kernel 接进 GPU 上跑的 GP 引擎,讲怎么用得省 | 进程内调用免来回搬数据 + warm-start 少迭代几次 + 同样时间下比 |

每个贡献的详细写法见 `contributions.md`。

## 怎么选材料:先多做,再挑

先把能做的实验和结论都做一遍(故意做多),然后挑结果最硬的放进 6 页,剩下的——多余的、不重要的、做出来不对的——扔掉。

每个贡献留一个"**必须有**"的结果,其他标上"**做出来好就加**"或"**地方不够就删**"。

记号:✅ 已经有 · ⚠️ 还要跑。

### C1 能选的材料

| # | 材料 | 想证明什么 | 有没有 | 怎么用 |
|---|---|---|---|---|
| a | 判据(5 条规则) | 能机械地判断一道 SR 题是不是真要在内部拟合常数 | ✅ e3 | **必须有** |
| b | 构造的题集 + 对照题(收 21 道,11 道对照一道没漏) | 能造出干净的正例和反例 | ✅ e3 | **必须有** |
| c | Feynman 34 道 → 只剩 2 道 的审计表 | 标准题库里这种题很少 | ✅ e3 | **必须有(至少一张表)** |
| d | 多个题库一起审计(Nguyen / Korns / Livermore / SRBench) | 把"很少"从一个题库扩到好几个,更站得住 | ⚠️ Korns 有底子,Nguyen/Livermore 要跑 | 做出来好就加 |
| e | 换不同的"现成常数"集合,留下的题在 0–11 道之间晃 | 老实说清楚结论对假设有多敏感 | ✅ e3 | 地方不够就删(挪脚注) |
| f | 不靠答案的对照测试(随机/常规起点,分别试不拟合内部/只线性/完整拟合) | 正例确实非内部拟合不可,反例不用 | ⚠️ 要跑 | 做出来好就加 |
| g | 判据被人挑刺后修过两处(trig 相位、可辨识性) | 判据经得起挑,不会错收错拒 | ✅ e3 | 地方不够就删(挪附录) |

**怎么选:** a+b+c 必上。看结果:d(几个题库都站得住才上,否则只放 Feynman 一张表)、f(对照测试干净才放)。地方紧:e 挪脚注,g 挪附录。

### C3 能选的材料

| # | 材料 | 想证明什么 | 有没有 | 怎么用 |
|---|---|---|---|---|
| a | 进程内调用,数据不在 CPU/GPU 之间来回搬 | kernel 能直接接进 GPU 上的 GP 引擎,数据留显卡里 | ✅(快多少要核一下) | **打底:证明能跑通** |
| b | 树的格式转换 + 核对(377 棵树一棵没转错) | 异构树能正确取出来喂给 kernel | ✅ e2 | 打底 |
| c | warm-start:从父代的常数接着拟合,迭代从 50 次降到 5–10 次 | 循环里不用每代从头拟合 50 次 | ⚠️ 要跑(plan E) | **最硬的结果候选** |
| d | 同样墙上时间下比(不拟合 / 从头 50 次 / warm 5 次) | 同样时间里 warm 少迭代更划算 | ⚠️ 要跑(plan D) | **最硬的结果候选** |
| e | 不用每代都拟合,隔几代一次效果一样 | 隔代拟合就够 | ✅ e4 | 省力的小结论 |
| f | fp32 的 kernel 质量和 fp64 的 scipy 一样,scipy 崩的地方它能跑完 | 又快又稳 | ✅ e4 | 稳定性证据 |
| g | 每代拟合花多少时间,拆开看 | 给"同样时间比"算成本 | ⚠️ 要测 | 配角 |

**怎么选:** 最硬的从 c、d 里挑一个(或都做、留好的)。a、b、f 已经有了,垫底保险。要是 c、d 都跑不出干净结果,C3 就只剩"能跑通"这点,那就退回下面的两个贡献。

**warm-start(C3-c)实现可行性已核(2026-06-24):比预想干净,最难的一层 EvoGP 已包掉。** EvoGP 把常数直接存在树节点的 `node_value` 数组里;交叉/变异的 CUDA kernel(`upstream/evogp/src/evogp/cuda/mutation.cu` 的 `_gpTreeReplace`)splice 子树时逐字节复制 value、只改 subtree_size,所以常数自动跟着子树继承——不用我们自己做"代际间常数对齐"那层难活。我们这侧只要加两个钩子(都用 `cusr/kernel/tree_interpreter.py` 已有的 node↔c_vec 映射):① 进 kernel 前把上一代 `node_value` 的常数 gather 成 `c_init`(kernel API 本来就吃 `c_init`,见 `cusr/kernel/co_inproc.py`);② 出 kernel 后把拟合好的常数 scatter 回 `node_value` 的 CONST 位置(现在缺这步——benchmark 只用结果算 fitness、不写回)。所以 warm-start **不是新算法**,工作量 ≈ 写回钩子 + c_init 接上一代 + 跑通"每代调 CO"的闭环;前提是 CO 已进 live loop(进程内调用已通,每代闭环 = 本条要做的事)。

## 退路:只做两个贡献

要是三个塞不下,或者 C3 的 D、E 实验没跑出干净结果,就把 C3 缩成 C2 评测里的一小节(说一句"能装进去用就行"),只留 C1 和 C2 两个扎实的贡献。这是最稳的 6 页写法。
