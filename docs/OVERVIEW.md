## 在做什么(一句话)

符号回归 = 让机器自动找一个公式去拟合数据。这里有一步:公式的形状定了之后,要把里面的
几个数字调到最合身。GPU 系统(EvoGP)**跳过这步**;CPU 系统(Operon / PySR)**做,但慢
或限量**。我们写了个 GPU 程序,**一次把一整代上千个公式的数字全调好**,并搭了个台子公平地
跟别人比。

## 手上有什么

- 一套测量台子 + **7 种"调数字"的方法**:scipy、Operon、PySR(两档预算)、我们的 GPU
  kernel(3 个版本)。
- **两种测试题**:3 批真的 EvoGP 进化出来的公式 + 3 批我们造的(有标准答案)。每批 4000 个。
- 一套口径:质量怎么算、速度怎么算、排好坏的顺序对不对。

## 跑出来的结果(笔记本,初步)

我们的 kernel(最好那版)对比 scipy:

| 题 | 快多少 | 调准的比例 |
|---|---|---|
| 常数少(简单) | 2.4–12× | ~90% |
| 常数多(难) | **23–29×** | 65–81% |

- **越难的活越占便宜**:常数多的时候 scipy 要 20 秒,我们 0.7 秒。
- **没人样样赢**:scipy 最准但慢;PySR 准但更慢(难题要 5 分钟);Operon 快但准头忽高忽低;
  我们又快、质量中上偏好。

## 已经定下来的几件事

- **fp32(单精度)就够用**,不上 fp64(EvoGP 和数据本来就是 fp32)。
- 主轴是**"又快又好"的权衡曲线**,不是一个单独的加速比数字。
- 测试题用 **EvoGP** 的——因为我们的程序是**装进 EvoGP** 用的;Operon / PySR 只当**比赛对手**,
  不当出题人。

## 还没做的

- **最急(6/16)**:把 kernel 装回 EvoGP,验证"有了它能不能多发现一类公式"(这步本地就能跑)。
- **等 A100**:正式速度数字、把 GPU 喂饱的大批量测试。
- **可选**:PySR 预算扫描、更多样的测试题、更强的 CPU 对手。
