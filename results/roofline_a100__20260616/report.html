Roofline (ANALYTICAL) — batch_lm_fusedfd on A100

2026-06-16

Question. Where does the fused-FD CO kernel sit relative to the A100 hardware ceilings — is it compute-bound, memory-bound, or far below the roofline (latency/occupancy/overhead-bound)? ncu (measured) is blocked by perf-counter permissions, so this is an analytical roofline.

Setup. Model FLOPs + DRAM bytes per the fusedfd algorithm (per LM iter, per tree), combine with the MEASURED end-to-end wall time from Tier0. Per-tree op histogram counted exactly from the synth early-gen M=16000 pop; mean iterations from the measured convergence curve. fp32. A100-SXM4-80GB peaks: 19.5 TFLOP/s fp32, 2039 GB/s HBM2e (ridge 9.56 FLOP/byte).

Findings

The kernel sits ~0.5-1% BELOW the A100 ceilings even when saturated — neither compute- nor BW-bound
Achieved 0.18% (M=16k) -> 0.38% (64k) -> 0.53% of fp32 peak (256k, saturated); 0.33% -> 0.96% of HBM peak. The BW-bound ceiling at AI=5.3 is ~10.8 TFLOP/s; achieved ~0.1 TFLOP/s is ~1% of even that. The binding constraint is execution efficiency / overhead, not the roofline.
Likely bottlenecks (for the optimization work): interpreter divergence + redundancy + host round-trips
Divergent switch-dispatch tree interpreter; warp-per-tree (32 threads stride N, low ILP, serial stack deps); 1-thread-per-tree K x K Cholesky (terrible occupancy); host-orchestrated LM loop with per-iter H<->D copies + ~8 kernel launches. fd_jacobian re-evaluates the WHOLE tree for each of the K perturbed columns (K full evals/tree/iter) — large redundancy.
If made efficient, the kernel would be (mildly) memory-bound on the J round-trip
Analytical AI = 5.3 FLOP/byte < ridge 9.56. The dominant modeled DRAM traffic is materializing J (K x N per tree) to global then reading it back in build_jtj. Fusing Jacobian -> JtJ accumulation (never materializing J) would raise AI and cut that traffic.
Achieved fraction rises with utilization, consistent with the throughput sweep
0.18% -> 0.53% of peak as M goes 16k -> 256k: more trees fill the 108 SMs, amortizing launch/host overhead — same story as the trees/s-vs-M curve saturating.

Caveats

  • ANALYTICAL, not ncu-measured. FLOPs use a disclosed op-FLOP table (arith=1, div/sqrt=4, transcendental=8); a different convention shifts AI and %-of-peak.
  • Achieved FLOP/s uses END-TO-END wall time, which includes host orchestration, per-iter H<->D copies, and kernel-launch latency — so it conflates GPU compute with overhead and UNDERSTATES per-kernel GPU efficiency. The 'far below roofline' gap is partly real GPU inefficiency, partly this overhead.
  • DRAM-byte model counts the J round-trip + y writes + bytecode and assumes xs/bytecode are largely L2-cached (amortized). Real DRAM traffic needs ncu.
  • mean_iters (12.58) estimated from a 5-iter-resolution convergence curve.
  • Per-tree distribution is synth early-gen (recoverable problem); late-bloated / inner-const-heavy differ (bigger trees, higher K).
